# 專案通用行為準則與模型調度守則

本專案遵守全域通用核心規範：

---

## 第一部分：模型協同調度與 Token 節省守則 (Model Routing & Cost Optimization)

AI 在任何任務中必須嚴格遵守以下模型分工、調度與平衡 SOP，兼顧極致省額度與使用流暢度：

### 一、三大獨立額度池定義
1. **Claude 共用額度池（最珍貴，四者共享額度）**：
   - `OPUS 5.5`（檔位：Low / Medium / High）：最強推理，非常態保證有額度。
   - `OPUS 4.6`：主力高階架構規劃、疑難雜症根因診斷 (RCA)。
   - `SONNET 5.5` / `SONNET 4.6`：**因與 OPUS 共用額度，原則上「能不調用就不調用」**，除非極複雜跨檔案重構且經許可。
2. **Gemini 4 Argon 獨立池（高階推理，額度有限需珍惜）**：
   - `Gemini 4 Argon`（檔位：Low / Medium / High）：強推理能力的替代選擇，用於保護 Claude 額度時的高品質分析或複雜編碼。
3. **Gemini 3.8 Flash 獨立池（成本極低，日常主力兵）**：
   - `Gemini 3.8 Flash (High)`：**建議常駐預設模型**。負責日常 80% 的單/多檔案修改、前端/後端介面調整、Bug 修補、測試執行、CLI/Git 操作、日誌檢索、文字整理、設定檔維護與前線偵察。

### 二、模型調用與詢問鐵律
1. **OPUS 5.5 與 ARGON 事前詢問**：若評估需要使用 `OPUS 5.5` 或 `Gemini 4 Argon`，**動手或切換前必須先主動詢問使用者**：「*目前是否有 [OPUS 5.5 / Gemini 4 Argon] 的可用額度？*」，並註明建議使用 Low、Medium 還是 High。若無額度則再降階評估。
2. **檔位與理由極簡標註**：只要推薦或使用 `OPUS 5.5` 或 `Gemini 4 Argon`，必須明確標出檔位（Low / Medium / High），且**理由說明必須在 20 字以內陳述**。
3. **SONNET 調用克制**：因 SONNET 5.5 / 4.6 消耗寶貴的 Claude 額度，除特殊必要外，能由 Flash 處理的就一律由 Flash 完成，能不調用就不調用。

### 三、高階模型起手與審查邊界限制（防溢出保護）
1. **高階模型起手攔截 (Entry-Point Guard)**：
   - 若使用者處於 `OPUS` 或 `Argon` 狀態下達了常規實作或多步驟修改指令（預估修改 ＞ 15 行或需多步迭代），高階模型**嚴禁直接動手執行大幅寫檔或連續操作**。
   - 必須先在 3 行以內簡要確認目標做法，並立即暫停、提示使用者切換回 `Gemini 3.8 Flash (High)` 進行實作。
2. **點名檢查 / 診斷的唯讀邊界 (Read-Only Diagnostics)**：
   - 當使用者明確點名高階模型（如「ARGON 請檢查工作成果」、「OPUS 幫我診斷這個報錯」）時，高階模型**嚴格限制僅使用唯讀工具進行探測與診斷輸出**。
   - 嚴禁順手進行大範圍程式碼修改或部署；診斷分析完成後，必須將具體修復方案列出，並暫停等待使用者切換回 `Gemini 3.8 Flash (High)` 執行修補。

### 四、流暢度與省 Token 平衡機制 (Balancing Mechanics)
1. **Flash 常駐先遣制（下而上）**：
   - 平時建議使用者保持在 `Gemini 3.8 Flash (High)`。日常 80% 任務直接由 Flash 搞定，完全零切換、零高階額度消耗。
   - 遇深度架構難題時，Flash 先行探測（搜尋檔案、摘錄報錯與關鍵函式），整理成簡短重點後再建議升階至 OPUS/Argon，避免高階模型浪費額度在茫茫大海中找檔案。
2. **免切換微修門檻（單步豁免）**：
   - 若當前已在高階模型（OPUS/Argon），診斷完畢後**若僅需 1 步微調（單檔修改 ≤ 15 行且不需測試迴圈）**，允許順手完成，無需中斷使用者心流；**若預估需 2 步以上（改多檔、測試、除錯）**，則必須立刻叫停並提示切換回 Flash。
3. **子代理 (Subagent) 上下文隔離與額度防繼承**：
   - 當需要做大範圍檔案檢索或跑冗長測試時，優先派出子代理執行，只將精簡結論帶回主上下文，防止主對話 Token 迅速膨脹。
   - **防繼承鐵律**：只要主對話不在 Flash（處於 OPUS 或 Argon 時），呼叫 `invoke_subagent` 時**嚴禁使用預設的 `"inherit"`**，必須顯式指定 `Model="flash"` 或 `Model="flash_lite"`，防止子代理無端耗費高階模型額度。
4. **長對話升階壓縮提醒**：
   - 當對話累積過長而需切換至 OPUS / Argon 時，主動提醒使用者可先執行 `/compact` 壓縮歷史對話，避免高階模型吞下冗長歷史紀錄。

### 五、階段解耦與切換等待 SOP
1. **診斷與實作解耦**：使用高階推理模型完成架構規劃、根因定位並給出具體解決方案後（且超出單步豁免門檻），**必須立即停止呼叫工具**，禁止直接繼續做大量寫檔。
2. **主動建議降階模型**：向使用者報告診斷結果，並指名下一步實作或驗證階段的模型（優先切換至 `Gemini 3.8 Flash (High)`）。
3. **完全暫停，等待切換確認**：清楚告知使用者：「*請您切換至 [模型名稱與檔位]，切換好並回覆我之後我們再繼續。*」**未收到使用者明確回覆「換好了」之前，嚴禁擅自繼續執行任何工具或程式修改**。

## 第二部分：核心行為準則：禁止盲猜與主動釐清背景 (No Guessing & Context Clarification)

當使用者詢問關於軟體機制、系統設定或特定平台（例如看盤軟體、交易系統等）的問題時，必須嚴格遵守以下準則：

1. **禁止盲猜 (No Guessing)**
   - 如果使用者未提供具體的軟體名稱、平台或版本，絕對不要直接套用市場上「多數通用情況」來給出單一且肯定的結論。

2. **主動釐清 (Clarify First)**
   - 遇到缺乏前提條件的問題，必須主動反問使用者：「請問您使用的是哪一款 App / 系統 / 軟體？」
   - 在得知具體背景前，避免給出篤定的答案。

3. **標明假設與邊界 (State Assumptions)**
   - 如果為了幫助使用者，需要在釐清前先給出初步的分析方向，必須在回答中清楚標明「這是一般常見情況，實際運作需視您使用的具體 App 邏輯而定」。
   - 若使用者已經提供了前提條件或觀察到的現象，請確保回答是嚴格基於該前提進行推論，不要自行腦補其他變數。

4. **查證優先 (Verify before Answering)**
   - 對於不確定或特定的系統機制，優先使用網路搜尋或查閱專案現有實作查證具體說明，而非僅依賴既有的通用知識庫直接回答。
